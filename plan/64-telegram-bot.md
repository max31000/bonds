# Задача 64 — Telegram-бот: подтверждения планов и команды

> **Кому адресовано.** `bond-implementer`. Контекст: дизайн §5 (Telegram), §11.
>
> **Зависимости:** 63. **Порядок:** после 63.
>
> **Рамки:**
> - Бот тот же (`Telegram:BotToken`).
> - Исполнения нет: approve переводит план в `Approved` (dry-run).
> - Webhook не делать — используем long polling.

---

## Что сделать

### 1. Резолв пользователя по Telegram

`users` ищется по telegram id: колонка уже используется в `UserProvisioning` по claim `tg` — сверить.

- Чужие tg-id и незарегистрированные — ответ «нет доступа», дальше никакой обработки.
- `OwnerId` не хардкодить: любой зарегистрированный пользователь сервиса управляет **своими** планами.

### 2. `TelegramBotPollingService` (BackgroundService)

- Long polling: `getUpdates`, `timeout = 25`.
- Offset хранить в новой таблице `bot_state` (`key`, `value`, миграция `034`), чтобы после рестарта не обрабатывать апдейты повторно.
- Сбой → `LogWarning`, пауза 5 с, следующая итерация. Токен бота в логи не попадает (как в `TelegramAlertSender`).
- **Конфликт:** если в проде включён другой потребитель `getUpdates` того же бота — проверить, что его нет.

### 3. `ITelegramBotClient`

Расширить отправку:
- `sendMessage` с `reply_markup` (inline keyboard) и `parse_mode=HTML` с экранированием;
- `editMessageText`, `answerCallbackQuery`.

Старый `ITelegramAlertSender.SendAsync(string)` не ломать.

### 4. Уведомление о плане

Когда `PolicyRunner` создаёт план `PendingApproval`, бот шлёт сообщение:
- правило и причина;
- строки: `КУПИТЬ TMON@ ×44 @ 166.57 ≈ 7 329 ₽, комиссия 0`;
- итоги, срок действия;
- пометка «режим наблюдения», если dry-run;
- кнопки `✅ Подтвердить`, `❌ Отклонить`, `🔎 Детали` (ссылка на `/bonds/plans/{id}`).

Для `AutoApproved` — информационное сообщение без кнопок.

Чтобы не спамить — **сводка раз в N минут**, если планов много (опция).

### 5. Callback

Формат: `p:{planId}:{action}:{nonce}`.
- `nonce` — случайные 8 байт base64url, хранится в плане.
- Проверки: пользователь — владелец плана, статус `PendingApproval`, срок не истёк, nonce совпал.

Дальше `approve`/`reject` через тот же сервис, что веб. Затем `editMessageText` с итогом («Подтверждено 14:05») и `answerCallbackQuery`.

### 6. Команды (только в личке с ботом)

| Команда | Действие |
|---|---|
| `/status` | капитал всего, корзины с drift, кэш, открытые планы |
| `/plans` | список открытых планов |
| `/inflow 50000` | P2-превью → создаёт план `PendingApproval` |
| `/withdraw 15%` · `/withdraw 50000` · `/withdraw 200 usd` | P5 |
| `/exit temporary` | выход из временной корзины |
| `/stop` | `user_settings.execution_paused = 1` (миграция 034), PolicyRunner перестаёт создавать `AutoApproved` (только `PendingApproval`), в фазе 3 исполнитель не отправляет ничего |
| `/resume` | снимает паузу |
| `/help` | список команд |

Парсер команд — чистая функция в Core с юнит-тестами: `%` → ДОЛЯ, валюта, мусор → подсказка.

### 7. Тесты

- Парсер команд.
- Callback: чужой план, истёкший, неверный nonce, повторное нажатие.
- Форматирование сообщения плана: эталонная строка, экранирование HTML.
- Polling — FakeHandler с последовательностью `getUpdates`; offset сохраняется.

## Критерии приёмки

- [ ] С прода: `/status` отвечает реальными цифрами; dry-run план приходит с кнопками; «Подтвердить» меняет статус в вебе.
- [ ] Нажатия чужих пользователей и повторные нажатия безопасны.
- [ ] pre-push-check зелёный.
