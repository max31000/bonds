> **Кому адресовано.** `bond-implementer`. Контекст: дизайн §5, решения §9 и §11; задачи 63 (планы) и 64 (бот).
>
> **Зависимости:** 63, 64.
>
> **Рамки:**
> - Только T-Invest. Freedom — задача 66.
> - Исполнение **выключено по умолчанию** на трёх уровнях:
>   1. Глобальный env `Execution__Enabled=false`.
>   2. Пользовательский режим `observe`.
>   3. Без торгового токена исполнение невозможно.
> - Боевое включение — только руками владельца, после его аудита безопасности.
> - Архитектурный тест задачи 63 переписать: отправка заявок разрешена **только** из `Bonds.Infrastructure/Execution/` и только через `ITInvestOrderGateway`.

## Модель

### Миграция `035`

| Таблица / колонка | Что |
|---|---|
| `user_settings.execution_mode` | `observe` \| `live`, дефолт `observe` |
| `trade_orders` | `plan_id`, `line_no`, `attempt`, `client_order_id` (UUID, UNIQUE — идемпотентность), `broker_order_id`, `status` (`New\|Submitted\|PartiallyFilled\|Filled\|Cancelled\|Rejected\|Failed`), `limit_price`, `lots_requested`, `lots_filled`, `avg_fill_price`, `executed_commission`, `currency`, `error_code`, `error_message` (без секретов), `created_at`, `updated_at` |
| `trade_plans.status` | добавить `Submitting\|PartiallyDone\|Done\|Failed` (если ещё не хватает) |

### Режим исполнения

`ExecutionOptions.EffectiveDryRun` теперь вычисляется. Live = **всё** из списка:
- `Execution__Enabled`;
- `user.execution_mode == live`;
- credential `tinvest_trade` в статусе ok;
- нет `execution_paused`.

Иначе — как сейчас, dry-run.

## Что сделать

### 1. Валидатор `tinvest_trade` (сеть)

- `GetAccounts` по торговому токену. Токен должен видеть **ровно один** счёт и иметь права `ACCOUNT_ACCESS_LEVEL_FULL_ACCESS`.
- Номер счёта должен совпадать с основным счётом пользователя (по `broker_account_id`).
- Иначе — invalid с понятной причиной: «токен на все счета — выпустите токен на один счёт», «нет прав на торговлю».
- В meta сохраняются только последние 4 символа номера счёта.

### 2. `ITInvestOrderGateway`

Единственный класс, который вызывает `OrdersService`:

| Метод | Вызов |
|---|---|
| `PostLimitOrderAsync(accountId, instrumentUid, direction, lots, priceQuotation, clientOrderId)` | `PostOrder` с `OrderType.Limit` и `order_id = clientOrderId` — идемпотентность на стороне брокера |
| `GetOrderStateAsync` | |
| `CancelOrderAsync` | |
| `GetTradingStatusAsync` | |

Цена облигаций передаётся в **пунктах**, фондов — в рублях за бумагу, через `Quotation`. Конверсия делается один раз и описывается doc-comment-ом.

### 3. `PlanExecutor` (BackgroundService, тик 20 с в часы торгов)

Берёт планы `Approved` и `AutoApproved` с `dry_run = 0` по пользователям в live. Для каждой строки:

**Предполётные проверки — любая не прошла → строка `Failed` с причиной, план `PartiallyDone`/`Failed`, уведомление в бот:**
1. Свежая котировка.
2. Отклонение mid от утверждённого лимита ≤ `Execution:MaxPriceDriftFraction` (0.002 фонды и акции, 0.005 облигации — значения дизайна §5, ревью 65).
3. Хватает денег — по `GetPositions`/`GetPortfolio` с учётом уже отправленных заявок.
4. `GetTradingStatus == NormalTrading`.
5. `api_trade_available`.
6. Дневной лимит авто пересчитан по уже исполненным сегодня (для AutoApproved).
7. Не стоит пауза.

**Отправка.** Продажи раньше покупок, по одной строке. `client_order_id` создаётся и **записывается в БД до отправки**. После рестарта сервиса заявка с тем же `client_order_id` проверяется через `GetOrderState` — повторно не отправляется.

**Сопровождение:**
- Не исполнено за `RepriceAfter` (5 мин) → отмена и перевыставление ближе к противоположной стороне стакана, но в пределах `MaxPriceDriftFraction` от исходного лимита. Не больше `MaxAttempts` (3).
- Затем `Expired` с уведомлением.
- За 10 минут до закрытия сессии висящие заявки отменяются.

**Завершение:**
- Полное исполнение → строка `Filled`; все строки исполнены → план `Done`.
- Синк портфеля сразу после исполнения.
- Сверка комиссии с моделью: отклонение > 0.01 ₽ → предупреждение в бот.

**Уведомления в бот:** отправлено, исполнено (цена, лоты, комиссия), ошибка, отменено. Кнопки нет, кроме «Отменить» для висящих заявок.

### 4. API и UI

- `PUT /api/settings/execution-mode {mode}`. Включение `live` требует:
  - валидный `tinvest_trade`;
  - подтверждение повторным вводом слова «LIVE» в UI;
  - сообщение в бот «Исполнение включено».
- На странице «Планы» — заявки по строкам и их статусы.
- Баннер «Режим наблюдения» показывается при dry-run; при live — «Исполнение включено» + кнопка «Остановить» (= `/stop`).

### 5. Тесты

- **Юнит** (fake gateway):
  - каждая предполётная проверка;
  - идемпотентность после «рестарта»;
  - перевыставление в пределах дрейфа;
  - продажи раньше покупок;
  - отмена перед закрытием;
  - сверка комиссии.
- **Интеграционные:** переходы статусов на MySQL, пауза останавливает исполнение, `execution_mode` и три ворот режима.
- **Песочница T-Invest:** опциональный тест под `[Trait("Category","Sandbox")]`, запускается только при наличии `TINVEST_SANDBOX_TOKEN` в env. Открыть sandbox-счёт → пополнить → лимитная заявка → исполнение → закрыть. В CI не запускается.
- Архитектурный тест: заявки отправляются только из `Execution/`.

## Критерии приёмки

- [ ] Без включения всех трёх условий ни одна заявка не отправляется (тест на каждую комбинацию).
- [ ] Песочница: заявка проходит путь Approved → Done (лог прогона приложить в отчёт).
- [ ] pre-push-check зелёный.
- [ ] Боевое включение — **не в этой задаче**, его делает владелец.
