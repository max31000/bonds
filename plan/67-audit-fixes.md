## Волна A — обязательно до включения live

1. **#1. Белый список автоисполнения в коде, не в БД.**
   - Авто разрешено только для корзины `code == liquidity` и только для бумаг класса **Fund** с `pays_distributions == false` (или по config-списку тикеров `PolicyOptions.AutoFundWhitelist`).
   - Проверка — в `PolicyRules` (статус `AutoApproved`) **и** в `ExecutionRules` (повторная проверка исполнителем).
   - `PUT /api/baskets/{id}` с `autoBuy/autoSell = true` для корзины не `liquidity` → 422.
   - Негативные тесты:
     - `ru_equity` с `autoBuy` → `PendingApproval`;
     - акция в `liquidity` → `PendingApproval`;
     - исполнитель отклоняет `AutoApproved`, подделанный в БД.
2. **#2. Резерв денег под `Approved` live-планы.** `ReservingCash` включает `Approved AND dry_run = 0` (и `Submitting`).
   - Тест: вечером одобрен live-план облигаций, в 10:00 P1 видит деньги за вычетом резерва.
3. **#3. Удержание денег под вывод.**
   - `summary.cashHold` у плана P5 / exit-basket — сумма к выводу. `SumReservedBuysAsync` учитывает hold.
   - P1 не работает, пока у пользователя открыт P5-план (Pending/Approved/Submitting) или не прошло `WithdrawHoldTtl` (дефолт 3 рабочих дня) с его исполнения. Вывод в банк делается вручную, поэтому hold снимается командой `/withdrawn` или кнопкой «Деньги выведены».
   - Тест: свободно 40k, вывод 100k → следующий P1 ничего не паркует.
4. **#4. Live-план в боте.**
   - В сообщении плана при `!DryRun` жирная строка «⚠️ РЕАЛЬНЫЕ ЗАЯВКИ» и `ExecutionNote`.
   - В списке `/plans` кнопок подтверждения для live-планов нет — только ссылка на детали.
   - В сообщении плана подтверждение в два шага: первое нажатие «Подтвердить» показывает список реальных заявок и кнопку «Отправить заявки», второе отправляет. Nonce одноразовый.
   - Тесты.
5. **#7. Неполные или устаревшие данные останавливают правила.**
   - `CapitalOverview`/`PolicyInput` получают `DataIncomplete` (нет цены хотя бы у одной позиции с ненулевым количеством, нет курса) и `StaleSince` (последний успешный синк брокера старше 26 ч).
   - При любом из них P3b, P4 и решение по дефициту для P2/P1 не строятся: причина в логе и в preview.
   - P1 при `DataIncomplete` по корзине ликвидности тоже не работает.
   - Тесты.

## Волна B — корректность

6. **#8.** Облигации с номиналом не в рублях в продажах P5/P4/exit: цена берётся в валюте цены без повторного умножения на курс, либо такие строки исключаются с причиной. Тест с Fx = 12.5 (CNY): количество бумаг верное.
7. **#10.** Дневной лимит авто считает только планы `decided_via = 'auto'` (в репозитории и в `AutoDayUsage`). Тест: ручная покупка на 200k не съедает авто-лимит.
8. **#11. Пауза и ворота не убивают планы навсегда.**
   - При закрытии ворот одобренные, но не начатые live-планы остаются `Approved` до истечения срока, а не `Failed`.
   - Начатые — отмена висящих заявок, план `PartiallyDone` или `Failed` с причиной.
   - Тексты `/stop` и `/resume` описывают поведение.
   - Тест: `/stop`, затем `/resume` в пределах срока — план исполняется.
9. **#17.** NotFound у отправленной заявки: перед закрытием её как `unknown_state` сверить по `GetOperationsByCursor` (сделки по инструменту после `created_at`) и восстановить `lots_filled`. Тест на fake.
10. **#12.** Статус авто в `PolicyKit` сравнивает рублёвые суммы (курс × сумма); лимиты включают комиссию. Задокументировать.
11. **#6.** Тариф Freedom обновляется в meta credential на каждом синке (`GetUserInfoAsync` уже вызывается). Тест.
12. **#9.** Комиссия Freedom: процентная часть округляется до центов **до** сложения с фиксом. Все 9 эталонов выписки — точное совпадение (`Be`, без допуска). Сейчас COPX 1.93 против 1.92, NDIA 1.54 против 1.53, SJPA 2.04 против 2.03.

## Волна C — устойчивость и безопасность

13. **#5.** `TInvestTokenProvider` и `TradingMetaRefresher` проходят по пользователям с валидным `tinvest_read`, а не берут глобального «primary». Синк T-Invest для каждого такого пользователя со своим токеном. Тест на двух пользователей.
14. **#15.** Токен Telegram в логах — защита не зависит от конфигурации логирования. `DelegatingHandler` подменяет путь `/bot<token>/` на `/bot***/` в `HttpRequestMessage` для логгеров. Проще: убрать `LoggingHttpMessageHandler` у именованных клиентов `telegram-bot*` через `RemoveAllLoggers()` / `ConfigureHttpClientDefaults`. Тест: правило `Logging:Console:LogLevel:Default=Information` не выводит токен.
15. **#13.** `PUT /api/baskets`: чтение, валидация и запись в одной транзакции с `SELECT ... FOR UPDATE` по корзинам пользователя. Ручной inflow и runner сериализуются тем же `GET_LOCK`, что исполнитель (или отдельным per-user lock).
